# Broker: plumb `amr` + `auth_time` through (Azure + Google) with log-only capture

## What to build

Carry the IdP's `amr` (authentication methods) and `auth_time` claims from both SSO providers through the polybag-connect broker to the tenant, and log them on each SSO login without gating anything yet. This is the log-only pilot: it produces real captured tokens so we can confirm what each provider actually asserts (folding in the former "verify assertions" step) before any skip logic is enabled in issue 03.

The broker already passes provider data to the tenant untouched: `OAuthController::callback` merges `getUserInfo()` into `$extra` ([OAuthController.php:166-181](../../../../polybag-connect/app/Http/Controllers/OAuthController.php)), which flows through the transfer payload and is returned verbatim by `/oauth/claim`. So adding `amr`/`auth_time` to the `getUserInfo()` return is all that's needed on the transfer path — no new endpoints, no signature changes (the HMAC covers the transfer *code*, not the payload).

**Azure** ([AzureOAuthProvider.php:48](../../../../polybag-connect/app/OAuthProviders/AzureOAuthProvider.php)) already decodes the ID token via `decodeIdTokenClaims()`; add `amr` and `auth_time` to the returned array. Confirm the claims are present in the v2.0 token (may require adding `amr` as an optional claim in the app registration / enabling via Conditional Access authentication context).

**Google** is wired as the `GenericOAuthProvider` and currently reads the **userinfo endpoint**, which does not carry `amr` — `amr` lives only in the ID token. Two pieces:
1. Promote `decodeIdTokenClaims()` up into `GenericOAuthProvider` (protected) and have its `getUserInfo()` merge `amr`/`auth_time` from `$tokens['id_token']` when present.
2. Add the request param to Google's authorize URL: `claims={"id_token":{"amr":{"essential":true},"auth_time":{"essential":true}}}`. The instance has already opted into the Google Security bundle (Authentication strength + Session age claims).

**Tenant** ([SsoCallbackController.php:59](../../app/Http/Controllers/Auth/SsoCallbackController.php)) reads `$data['extra']['amr']` and `$data['extra']['auth_time']` alongside `user_email` and logs them (no behavior change). The `bypass_broker` dev path can be deferred/noted since it isn't the production flow.

## Implementation

**Implemented — awaiting review.** Spans both repos.

**polybag-connect (broker):**
- `GenericOAuthProvider` now owns `decodeIdTokenClaims()` (promoted from Azure, protected) plus a new `authClaimsFrom()` that returns only the present `amr` / `auth_time` keys. `getUserInfo()` merges those onto the profile via the spread operator, so absence adds nothing (existing exact-match `getUserInfo` tests stay green).
- `getAuthorizationUrl()` merges an optional `authorize_params` config array; Google's provider config sets `authorize_params.claims` to the OIDC request for `amr` + `auth_time` (Security-bundle features already opted in on the app).
- `AzureOAuthProvider` drops its private decoder (inherits the base), and its ID-token path now spreads in `authClaimsFrom($claims)`; the Graph fallback picks them up through the generic path.
- Nothing else on the transfer path changed — `extra` already flows verbatim through the transfer/claim exchange, and the HMAC covers the transfer code, not the payload.

**polybag (tenant):**
- `SsoCallbackController::receive()` reads `extra.amr` / `extra.auth_time` and logs them (`logger()->info("SSO login MFA assertion …")`) on every broker SSO login. Log-only — no gating.

Tests: broker `GenericOAuthProviderTest` + `AzureOAuthProviderTest` (amr/auth_time surfaced, omitted when absent, no-userinfo path returns only auth claims, authorize URL carries the `claims` param); tenant `SsoLoginTest` asserts the assertion is logged. Broker suite 24 passing; tenant SSO/MFA suites 35 passing.

**Capture results (2026-07-23):**
- **Azure — confirmed working.** After adding `amr` + `auth_time` as ID-token optional claims on the app registration, a real work/school account emitted `amr: ["pwd","totp","mfa"]` + `auth_time`, forwarded end-to-end (`tid: fc6cceae-…`). `mfa` present. `amr:mfa` is reported even on silent SSO when the session already satisfied MFA. Personal MSA accounts (`tid: 9188040d-…`) emit no `amr` regardless — dead end, exclude from trust.
- **Google — partial.** `amr`/`auth_time` flow, but only `["pwd"]` captured so far because Google keeps skipping the second factor on trusted sessions (and an intermittent Google-side 500 in incognito, possibly aggravated by the `essential:true` claims request). Still need an `amr:["…mfa…"]` capture from Google.

The remaining Google capture is the last precondition for enabling `trust_idp_mfa` in issue 03. The `bypass_broker` direct-Socialite path was left unchanged (out of scope; not the production flow).

### Follow-up from code review — ID-token verification (done)

Code review flagged [P1]: the broker only base64-decoded the ID token before exporting `amr`/`auth_time` as authentication-strength evidence — no signature/issuer/audience/expiry checks. Fixed in the broker before deploy:

- Added `firebase/php-jwt` (broker-only; the tenant never sees the ID token).
- `GenericOAuthProvider::verifyIdToken()` now verifies the RS256 signature against the provider's JWKS (fetched + cached 6h, with a one-shot refresh on key rotation), then checks `aud == client_id`, `exp`/`nbf` (via the library), and `iss`. **Fails closed** — any failure returns null and the `amr`/`auth_time`/`tid` claims are dropped (Azure email then falls back to Graph; Google to userinfo).
- Config gained `jwks_uri` + `issuer` per OIDC provider. Azure is **multi-tenant (`common`)**, so the issuer is validated as `https://login.microsoftonline.com/{tid}/v2.0` with `{tid}` substituted from the token's own `tid` claim (self-consistency), not a pinned string.
- This also hardens the pre-existing (unverified) email trust.

Tests rewritten to sign tokens with a generated RSA key and serve the public half as a faked JWKS (`Tests\Support\SignsIdTokens`); added negative cases for unsigned/tampered, wrong-audience, expired, and inconsistent-`tid` tokens. Broker suite 50 passing.

### Second review round — validate the signing key's issuer (done)

Code review flagged [P1] again: the multi-tenant check validated only the token's self-declared `iss`/`tid`, not whether the *signing key* was authorized for that tenant, and `JWK::parseKeySet()` discards the per-key `issuer` the /common JWKS carries. Also, Microsoft requires `tid` to be a GUID (the old `contoso-tid` test would have wrongly passed). Fixed:

- Verification now matches the raw JWK by `kid` (preserved alongside the parsed keys) and, when the key declares an `issuer` (Azure /common), binds the token: `tid` must be a GUID **and** the token `iss` must equal the key's issuer with `{tenantid}` replaced by that `tid`. Providers whose keys carry no issuer (Google) still validate against the configured `issuer`. Ref: Microsoft "validate the signing key issuer".
- Removed Azure's config `issuer` template — the signing key is now the source of truth (fail-closed if a key ever lacks an issuer).
- Tests use real GUID `tid`s and a key-level `issuer`; added cases proving a token whose `iss` names a different tenant than the key authorizes is rejected, and a non-GUID `tid` is rejected. Broker suite 51 passing.
