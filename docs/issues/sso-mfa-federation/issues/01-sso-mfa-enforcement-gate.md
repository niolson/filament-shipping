# SSO MFA enforcement gate (close the bypass)

Status: ready-for-human — implemented, needs review
Category: enhancement
Type: AFK

## Parent

`docs/issues/sso-mfa-federation/PRD.md`

## What to build

Close the security hole where SSO logins skip the app's MFA requirement entirely. Today all three SSO callbacks (`GoogleController::callback`, `AzureController::callback`, `SsoCallbackController::receive`) call `Auth::login()` directly and land on `/`, bypassing Filament's login-time challenge; the `require_mfa` middleware only enforces that a factor is *enrolled*, not that it was *used this session*.

Introduce a **fail-closed, SSO-only post-login gate**: after an SSO `Auth::login()`, if `require_mfa` is on and the user has an enabled MFA provider, mark the session as MFA-pending and force a custom challenge before any panel access is granted. No `amr` handling in this slice — absence of an IdP assertion is the only behavior, so the gate always fires when MFA is required. Password-login users keep Filament's native challenge and are untouched.

Reuse only the public verification primitives — do not reimplement TOTP or fork Filament's login flow:
- `AppAuthentication::verifyCode()` and `verifyRecoveryCode()` ([AppAuthentication.php:170](../../../vendor/filament/filament/src/Auth/MultiFactor/App/AppAuthentication.php))
- The `EmailAuthenticationForEmailUsers` equivalent for email-based users

Shape:
- SSO callbacks set a `sso_mfa_pending` session flag (instead of proceeding to `/`) when `require_mfa` is on and a provider `isEnabled($user)`.
- A custom middleware on authenticated panel routes redirects `sso_mfa_pending` sessions to a custom challenge route (allowlisting the challenge route and logout).
- A minimal Livewire challenge page accepts a code / recovery code, verifies via the provider primitive, clears the flag on success, then proceeds.
- Not-enrolled SSO users are already handled by Filament's existing `EnsureMultiFactorAuthenticationIsEnabled` (forces enrollment); this gate only covers the "enrolled but not exercised this session" case.

## Acceptance criteria

- [ ] With `require_mfa` on, an SSO user who has TOTP enrolled is forced through the custom challenge before reaching the panel; a valid code grants access, an invalid one does not
- [ ] Recovery-code path works via `verifyRecoveryCode()`
- [ ] Email-MFA users (`EmailAuthenticationForEmailUsers`) are challenged via their provider's verification
- [ ] Fail-closed: no bypass of the gate by navigating directly to any panel route while `sso_mfa_pending` is set; only the challenge route and logout are reachable
- [ ] Password-login users are unaffected (Filament's native challenge still governs them; no double challenge)
- [ ] SSO user with no enrolled factor is still routed to Filament's enrollment setup (existing behavior preserved)
- [ ] Rate-limiting / lockout parity consistent with the existing login challenge behavior
- [ ] Pest feature tests cover: enrolled-SSO forced challenge, invalid code rejected, recovery code, direct-route bypass attempt, password-user untouched
- [ ] Applies to all three SSO entry points (Google, Azure, broker `SsoCallbackController`)

## Agent Brief

**Category:** enhancement
**Summary:** Close the SSO MFA bypass with a fail-closed, SSO-only post-login gate.

**Current behavior:**
SSO authentication logs the user in directly and lands them on the panel without ever invoking the panel's login-time MFA challenge. The panel's "require MFA" setting only activates the enrollment-check middleware, which enforces that a factor is *enrolled* — never that it was *exercised this session*. Result: with MFA required, an SSO user who has enrolled an authenticator app reaches the panel with no code, every login. Password-login users are correctly challenged because they go through the framework's login component.

**Desired behavior:**
After an SSO authentication, when the panel requires MFA and the user has at least one enabled MFA provider, the session is marked MFA-pending and the user must complete a challenge before any panel route is reachable. Fail closed: this slice consults no IdP signal, so the challenge always fires when MFA is required. Password-login users are unaffected — no double challenge. An SSO user with no enrolled factor must still be routed to the framework's enrollment flow (existing behavior preserved).

**Key interfaces:**
- The three SSO entry points (Google callback, Azure callback, and the broker "receive" handler) — after authenticating, set a session "MFA pending" marker instead of redirecting into the panel, when MFA is required and some MFA provider reports enabled for the user.
- A guard on authenticated panel routes that redirects MFA-pending sessions to a dedicated challenge route, allowlisting only that challenge route and logout.
- A challenge component that verifies a submitted code or recovery code using the MFA providers' existing public verification methods (the authenticator-app provider exposes code and recovery-code verification; the email provider exposes its own). On success it clears the pending marker and proceeds.

## Implementation

**Implemented — awaiting review.** Deferred-authentication design (see review round below for why the first, middleware-based design was replaced).

- `SsoLoginService::completeLogin()` is the single decision point. When `require_mfa` is on **and** the user has an enabled MFA provider, it **does not authenticate** — it stashes `sso_mfa.user_id` + `sso_mfa.remember` in the session and redirects to the login route. Otherwise it `Auth::login(remember: true)` and redirects to `/`. Users with no enrolled factor fall through to Filament's own `EnsureMultiFactorAuthenticationIsEnabled` enrollment gate (unchanged).
- All three SSO callbacks (`GoogleController`, `AzureController`, `SsoCallbackController`) return `SsoLoginService::completeLogin($user)`.
- The **guest login page** (`App\Filament\Pages\Auth\Login`) renders the challenge for a pending SSO user: `mount()` sets `userUndertakingMultiFactorAuthentication` from `sso_mfa.user_id` (reusing Filament's challenge form + each provider's `getChallengeFormComponents()`), and `authenticate()` branches to `completeSsoMfaChallenge()` — which validates the code/recovery code, then `Filament::auth()->login($user, $remember)` and `session()->regenerate()`. The remember cookie is minted **only here**, after the factor passes. Per-user rate limiting matches the login challenge.

### Review round — deferred auth (two [P1]s fixed)

The first design logged the user in immediately and gated with `EnsureSsoMfaChallengeComplete` middleware on the panel. Review found two bypasses, both fixed by deferring authentication entirely:

- **[P1] Remember cookie bypassed MFA.** `Auth::login(remember: true)` minted a persistent cookie before MFA, while the pending flag was session-only — a lost session + surviving cookie could authenticate without the flag. Now nothing is authenticated (no cookie) until the challenge passes.
- **[P1] Middleware only covered Filament routes.** The authenticated user could reach non-panel `auth` routes (`/qz/sign`, `/qz/provision-script/*`, `pick-batches/*/summary`, `.../pack-slips`). Deferring auth means the pending user isn't authenticated, so every `auth`-gated route bounces them to the login challenge — no per-route middleware coverage to get wrong.

Removed: `SsoMfaChallenge` page + view, `EnsureSsoMfaChallengeComplete` middleware, and its panel registrations.

**[P1] Follow-up — challenge/login-target confusion (fixed).** The challenge form validated the user encrypted in `$userUndertakingMultiFactorAuthentication` (set at mount), but the login used `session('sso_mfa.user_id')` read fresh. Two SSO attempts in separate tabs could overwrite the session user, so a stale form would validate user A's code and then authenticate user B. `completeSsoMfaChallenge()` now decrypts the challenge user id and, before validating, requires it to `hash_equals` the session user id — otherwise it clears the pending state (`clearSsoMfaChallenge()`, which also nulls the property) and rejects. Test added: `rejects a stale challenge when a second SSO attempt changed the pending user`.

Tests: `tests/Feature/SsoMfaChallengeTest.php` (9 passing) — decision logic; **not authenticated + no remember cookie while pending**; a pending user is bounced from `/qz/provision-script/*`; login-page challenge renders; valid TOTP authenticates; invalid TOTP stays unauthenticated; recovery code. Full suite 1248 passing.

**Review notes:** the email-MFA path is covered at the decision level (email-only user is gated) but the full email send/verify round-trip isn't exercised automatically — worth a manual check.
